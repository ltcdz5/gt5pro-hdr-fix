# 技术说明

## 它拦截的是什么

DSPP 的 **3D gamut 表**（17×17×17，每项 12 bit，整表 39536 字节）。

进入 HDR 模式时，驱动调用：

```
reg_dmav2_setup_dspp_3d_gamutv43(struct sde_hw_dspp *ctx, void *cfg)
```

其中 `cfg->payload` 指向驱动缓存的表数据，`cfg->len = 39536`。
本模块用 kprobe 挂在这个函数上，把 payload 的内容整体替换成校正后的表。

之所以能持久：`payload` 指向的是驱动自己缓存的 blob（不是栈上临时结构），
改它就是改驱动状态；而 HDR 期间驱动不会再次重写，所以一次替换管整个会话。

## 为什么只影响 HDR：白名单

**默认放行，只有明确认出的才动。**

```
if 指纹 == SDR 指纹            -> 原样放行（最高优先级）
else if 指纹 == 横屏 HDR        -> 用横屏手调表替换
else if 指纹 == 竖屏 HDR
     或 白点蓝明显偏低(B/R<0.97) -> 用竖屏补蓝表替换
else                            -> 原样放行
```

半屏 HDR + SDR 界面走的正是**竖屏 HDR** 这条路线：SurfaceFlinger 把 HDR 色调映射后
产出的表与竖屏 HDR 一致（或白点蓝偏低），因此同样会被替换成补蓝表。

这是本项目踩过最大的坑：

| 曾经的做法 | 后果 |
|---|---|
| 黑名单：排除 SDR 指纹就替换 | SDR 指纹也会变，漏一个就把整个桌面染蓝 |
| 黑名单：白点蓝低就补 | SDR 也可能蓝低，误伤 |

**教训：识别必须做成白名单。黑名单漏一项就出事，而且是在用户桌面上出事。**

实测 SDR 桌面 822 次调用全部走第一分支（放行），零误替换。

## 表的编码

```
struct drm_msm_3d_gamut {
    u64 flags;
    u32 mode;                  // 必须为 1（mode 17）
    u32 scale_off[3][16];
    struct drm_msm_3d_col col[4][1229];   // 偏移 204，共 39328 字节
};

struct drm_msm_3d_col {
    u32 c2_c1;   // 高 16 位 = G，低 16 位 = B
    u32 c0;      // R
};
```

**通道映射：c0 = R，c1 = B，c2 = G。**

注意 **c1 是蓝，不是绿**——这一点搞错会让所有调色都往绿色跑，
是本项目踩过最大的第二个坑。确定方法：给三个通道不同的增益，拍屏幕比对。

网格索引：

```
n = g*289 + b*17 + r      // r 变化最快
entry = n / 4             // 项内偏移
table = n % 4             // 表偏移
地址 = COL_OFF + (n/4)*8 + (n%4)*1229*8
```

## 校正曲线

### 横屏（最终版）

分三步叠加，基准是**原厂 HDR 表**（保持亮度）：

1. **只补蓝**：B 通道随电平提升（高光 +22%、中段 +30%）
   - 不动 R/G，白点亮度不变
2. **压 R/G 高光**：x>0.5 后逐渐压到 0.86，修正白点偏黄
3. **末次微调**：R 全段 ×0.96、G 全段 ×0.98（按实测灰点 R 偏高 3.7% 校准）

最终白点：`R=3232 B=4095 G=3297`，实测灰点 `#a7a1a1` 修正后接近中性。

### 竖屏

竖屏原厂表白点 `4074/3852/4095`（蓝比红低 5.4%），只需 B 通道 ×1.20：

```
white  R=4074 B=4095 G=4095   B/R=1.005
gray   R=2049 B=2315 G=2058   B/R=1.130
```

**关键原则：补蓝而不是压 R/G。** 压 R/G 会直接降低亮度，
这是最初走弯路的原因（白点从 4085 掉到 2411，掉了 41%）。

## 重新生成表

横屏：

```bash
python3 tools/gain5.py 0.70 -0.11 0.755 -0.135 1.03 -0.28 out.bin
```

竖屏：

```bash
python3 tools/gain_port.py 112 base_portrait.bin out.bin
```

## 调参 WebUI

在 KernelSU 管理器里点模块的「打开」即可进入。三个滑块直接对应 R/G/B 增益：

| 控件 | 范围 | 作用 |
|---|---|---|
| 红 R | 70%–110% | 画面偏红偏黄就减，偏青就加 |
| 绿 G | 70%–110% | 偏绿就减，偏紫就加 |
| 蓝 B | 70%–170% | HDR 发黄主要靠它：偏黄就加，偏紫就减 |

点「应用」后立即生效，参数存到 `/data/adb/hdrfix.conf`，生成的表存到
`/data/adb/hdrfix/land_custom.bin`，`post-fs-data.sh` 会在开机时自动加载。

实现方式：页面里的 JS 读入 `base_land.bin`（原厂横屏表），按增益重算 17³ = 4913 个格点，
再分块 base64 传到设备解码写入 `/proc/sdehdrlut_land`。设备端不做二进制运算。

**经验值**：蓝 130–140% 能明显改善发黄；超过 145% 灰阶会发紫。白点处 B 已接近满量程，
再想更蓝只能减 R（会略降亮度）。

## 调试接口

```bash
su -c 'cat /proc/sdehdrstat'          # 命中统计 + 最后一次的表指纹/白点
su -c 'cat /proc/sdehdrlut_land > /sdcard/land.bin'
su -c 'cat /sdcard/new.bin > /proc/sdehdrlut_land'   # 换表（下次 HDR 切换生效）
```

`/proc/sdehdrstat` 输出示例：

```
calls=822 land=0 port=0 other=822 fp=0x8777be4f white=4045/4095/4092 en=1
```

- `calls` 总调用次数
- `land` / `port` 横屏/竖屏表命中次数
- `other` 原样放行次数（SDR 应全部落在这里）
- `fp` / `white` 最后一次见到的表指纹与白点

## 附：这个机制的潜力与边界（仅供参考）

本模块只做了一件事：修 HDR 偏黄。但它的挂载点本身比较通用，记在这里供后来者参考。

### 挂的是什么

```c
.symbol_name = "reg_dmav2_setup_dspp_3d_gamutv43"
```

DPU 里配置 DSPP **3D gamut v4.3** 的函数（走 `reg_dmav2` LUTDMA 通道）。
入参 `struct cp_cfg_head { void *payload; u32 len; }`，只在 `len == 39536` 时动手，
直接把校正表 `memcpy` 进驱动缓存的 payload。

换句话说：**这是一个 17³ 三维 LUT 的注入点**，可以任意改写显示的三维色彩变换。

### 理论上可用于（均未实现、未验证）

- 自定义色温 / 色调 / 饱和度 / 色域映射
- 护眼、夜间、阅读等场景化偏色
- 用测量数据生成 LUT 做校色（类似 DisplayCAL 的做法）
- 按 HDR / SDR / 横竖屏分场景切换不同表

### 保守的边界说明

写这些不是承诺，而是把已知的坑先讲清楚：

| 限制 | 说明 |
|---|---|
| 只有一个注入点 | 只覆盖 3D gamut 这一级，且要求 `len == 39536`。PCC（逐通道曲线）、IGC（逆 gamma）、GC（gamma）、VLUT 是**别的块、别的函数**，需要各自挂钩子，本模块未覆盖 |
| SDR 是全系统共用 | 所有 SDR 内容用同一张表。改 SDR 等于改整个 UI（桌面、微信、相机预览一起变），风险远高于 HDR。本项目因此把 SDR 指纹设为最高优先级放行 |
| 没有逐应用信息 | 驱动侧看不到前台应用。要按应用切表只能在用户态轮询前台再写 `/proc`，有约百毫秒延迟，切换时可能看到闪变 |
| 指纹随固件变化 | `SDR_FNV` / `LAND_FNV` / `PORT_FNV*` 都是设备+固件绑定的常量，OTA 或换机型后必须重新采集 |
| 时序依赖 | 替换必须发生在帧被使用之前。HDR 会话有缓存所以一次替换管全程；模式切换时驱动会重写，每次都要接住 |
| 热路径限制 | kprobe 在显示热路径上，**绝对不能带 printk**，否则 printk 风暴会把系统拖死。只能累加计数器，卸载时一次性打印 |

### 结论

适合做**显示侧后处理**（场景化 LUT、校色、护眼），不适合替代系统色彩管理：
线性域的 gamma / 白平衡、硬件色域切换、HDR 元数据处理都不在这条链路上，
硬要做得再挂多个钩子并改 HAL/SF 侧，复杂度和风险会显著上升。

## 调试技巧

想知道某个场景到底用了哪些表，可以写一个只记录不修改的探针
（见开发记录里的 sidecar56），按"首次出现"打印指纹和白点。
比猜测快得多。

注意：**热路径上的 kprobe 绝对不能带 printk**，会 printk 风暴把系统拖死。
需要观测时用计数器，卸载时一次性打印。
